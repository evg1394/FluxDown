# FluxDown RU Fork — AI Handoff / инструкция для продолжения работы

> **Сначала прочитать этот файл целиком при возобновлении работы.** Это рабочая инструкция для ИИ, который продолжает сопровождать форк `evg1394/FluxDown`. Не считать память предыдущего чата единственным источником истины: сверять GitHub и актуальное состояние веток, Actions и Releases.

## 1. Цель проекта

Поддерживать форк FluxDown с полноценной русской локализацией и рабочей сборкой Windows Installer для пользователя, который не собирает проект локально и проверяет готовый EXE.

Основной репозиторий форка: https://github.com/evg1394/FluxDown  
Upstream: https://github.com/zerx-lab/FluxDown  
Текущая рабочая ветка синхронизации/сборки: `sync-upstream-2026-10-23`  
Ветка по умолчанию: `main`

Главный пользовательский результат: установщик с именем вида
`FluxDown-ВЕРСИЯ-RU-windows-x64-setup.exe`
(фактический пример для версии 0.6.1: `FluxDown-0.6.1-RU-windows-x64-setup.exe`).

## 3. Обязательные правила работы

1. Работать непосредственно с GitHub через доступные GitHub-инструменты; пользователь не работает с локальной копией проекта.
2. Перед изменениями выяснить актуальные HEAD и статус веток, upstream и недавних Actions runs. Не предполагать, что SHA и статус из этого файла всё ещё актуальны.
3. Основной сценарий — сохранить форк-специфичные изменения и при необходимости обновить исходники из upstream. Не делать слепую замену всего `main` и не переносить оригинальные release-workflows без анализа их последствий.
4. Не допускать, чтобы приложение форка обращалось к upstream API релизов оригинала для проверки обновлений. Проверять исходный код и переменные окружения в сборочном workflow.
5. Локализация: сравнивать ключи `assets/i18n/en.json` и `assets/i18n/ru.json`; сохранять все ключи, плейсхолдеры (`{name}`, `{count}` и т. п.), escape-последовательности и форматирование. Новые английские значения переводить, технические названия/бренды оставлять только когда это уместно. Проверять также кастомные строки `installer/windows/setup.iss`.
6. Не запускать несколько конкурирующих Windows build runs, если workflow переписывает один и тот же release tag: устаревший запуск может перезаписать тег или артефакт. Дождаться нужного run и проверить SHA, artifact и release asset.
7. Не говорить «готово/успешно», пока GitHub не подтвердил результат. Если пользователь сообщил, что установил и проверил сборку, считать это подтверждением пользовательского smoke test, но всё равно проверять новый артефакт отдельно.
8. Не менять секреты, не выводить секреты в логи и не удалять workflows без проверки назначения, триггеров, зависимостей и влияния на upstream-функциональность.

## 4. Сборка и выдача Windows Installer

Основной файл: `.github/workflows/build-windows.yml`.

Перед запуском:
- проверить, что выбран правильный ref/commit;
- проверить последние runs и убедиться, что нет конфликтующей сборки, обновляющей тот же tag;
- проверить, что локализация и fork updater guard входят в выбранный commit.

После сборки проверить:
- run завершился с `conclusion: success`;
- `head_sha` соответствует нужному commit;
- артефакт содержит `FluxDown-*-RU-windows-x64-setup.exe`;
- GitHub Release имеет корректный asset с тем же именем;
- release tag указывает на ожидаемый source commit.

Не выдавать старый артефакт только потому, что он доступен. Ссылку давать лишь после проверки текущего артефакта/release.

## 5. Workflow-файлы: назначение

В каталоге `.github/workflows/` на ветке `sync-upstream-2026-10-23` проверено **12 workflow-файлов**. В GitHub Actions было **89 запусков (runs)** на момент проверки — это история выполнений, а не 89 отдельных workflow-файлов. Не удалять историю запусков и не удалять workflow только ради уменьшения числа runs.

- `android-package.yml` — сборка/пакетирование Android.
- `build-windows.yml` — наша специализированная Windows x64 RU-сборка и обновление asset в Release; критически важен.
- `ci.yml` — проверки проекта и сборки при CI.
- `deploy-website-v2.yml` — необязательный деплой нового сайта; зависит от deploy secrets.
- `gpui-debug-package.yml` — ручная отладочная сборка GPUI для диагностики.
- `ios-sideload.yml` — workflow для iOS sideload-пакета/подписания.
- `ios-testflight.yml` — сборка/публикация iOS в TestFlight.
- `plugin-sdk-release.yml` — публикация пакета plugin SDK по специальному тегу.
- `release-auto-rerun.yml` — автоматический повтор отдельных упавших релизных jobs; проверить триггеры прежде чем менять.
- `release.yml` — комплексная upstream release-пайплайн для множества платформ и компонентов; большая, с внешними секретами/публикациями. Не запускать вручную и не удалять без понимания side effects.
- `test-package.yml` — ручная сборка тестовых пакетов для платформ.
- `website-ci.yml` — CI для документации сайта при PR.

### Политика очистки workflows

Сначала отличать:
- **workflow-файлы**: YAML в `.github/workflows/`;
- **runs**: история запусков этих workflows;
- **jobs/steps**: части одного запуска.

Сначала перечислить файлы и разобрать `on:`, jobs, секреты и side effects. Сохранять CI, основной RU Windows build, используемые вручную тестовые пакеты и нужные upstream-процессы. Если workflow не нужен форку, безопаснее сначала отключить его или ограничить триггеры, чем удалять файл: это позволяет не потерять upstream-функциональность при следующей синхронизации. Удаление допустимо только после подтверждения, что workflow не используется и его side effects не нужны.

## 6. Синхронизация upstream

Перед sync:
1. Получить свежие commits/refs upstream `zerx-lab/FluxDown` и форка.
2. Сравнить изменения upstream с текущим форком и определить конфликты.
3. Особое внимание: `assets/i18n/ru.json`, `installer/windows/setup.iss`, `.github/workflows/build-windows.yml`, `native/agent/src/update/release.rs`, website deploy workflow и release/tag logic.
4. Переносить новые функции upstream, не затирая русский перевод, суффикс `-RU`, fork updater guard и защиту необязательного website deploy.
5. После sync выполнить сравнение ключей локализаций и проверить workflow-триггеры/имена артефактов.
6. Сборка Windows запускается только после проверки, что изменения совместимы.

## 7. Следующий шаг при возобновлении

1. Прочитать эту инструкцию.
2. Проверить GitHub branch heads, workflow files, recent runs и текущий Release/tag.
3. Уточнить актуальную задачу пользователя по последнему сообщению; не повторять уже завершённый перевод/сборку без причины.
4. Если пользователь просит «проверить workflows», начать с точного списка файлов и их триггеров. Сейчас 12 YAML-файлов; 89 — количество запусков, а не количество файлов.
